# Ciena SAOS 10 by SNMP

## Overview

This template monitors Ciena packet networking platforms running **SAOS 10** (the 392x/3931, 394x, 398x, 513x, 5144, 516x, 517x, 518x and 81xx families) over SNMP. It combines SNMP polling (v2c or v3) with SNMP traps, because several things an operator cares about on SAOS 10 (chassis health, PSU and fan transitions, dying gasp, configuration changes, module state) are only reported as notifications.

Polled over SNMP:

- System identity, uptime and inventory: SNMPv2-MIB, HOST-RESOURCES-MIB and the ENTITY-MIB chassis row (model, part number, serial number, hardware revision, running SAOS release).
- CPU, memory and filesystems from UCD-SNMP-MIB (the only CPU source on SAOS 10; `/mnt/apps`, `/mnt/config`, `/mnt/log`, `/mnt/secure` and `/tmp` are discovered).
- Temperature sensors, fans and power supply output voltage from LM-SENSORS-MIB (the only SNMP GET path to environmental data on SAOS 10).
- Network interfaces from IF-MIB with 64-bit counters, errors, discards and the RMON CRC/alignment error counter per physical port. Only physical ports (`ethernetCsmacd`) and LAGs are discovered by default: SAOS 10 also lists its logical ports, flow points/sub-ports and management interfaces in IF-MIB, and a service edge can have thousands of those rows.
- Transceiver digital diagnostics (temperature, supply voltage, laser bias, Rx/Tx optical power) from CIENA-CES-PORT-XCVR-MIB. The alarm thresholds programmed in each transceiver are read at discovery time and used by the trigger prototypes, so no site-specific optical thresholds have to be configured.
- Module state, last reboot reason, running release and software partitions from CIENA-CES-MODULE-MIB (one module on fixed-configuration platforms, one per slot on modular chassis).

Received as SNMP traps (`snmptrap[...]` items, grouped by function, plus `snmptrap.fallback` for everything else): link up/down, dying gasp, chassis health, power supply, fan speed, platform hardware, module state change, reboot, configuration change, transceiver thresholds and inventory, SNMP authentication failure, security/AAA, routing protocols (BGP, OSPF, IS-IS, LDP, BFD), CFM, MPLS services (L3VPN, EVPN, EFD) and synchronization/PTP. Chassis health and AAA server traps also feed small state items, so those problems recover when the "good" or server status notification arrives. Power supply, fan, transceiver inventory and VRF / EVPN segment problems are closed manually, because their notifications are not tracked per unit (see [Known limitations](#known-limitations)).

The template uses **numeric OIDs only**; no MIB files have to be installed on the Zabbix server or on the trap receiver. Do **not** load the Ciena MIBs into `snmptrapd`: the trap items match the numeric notification OIDs (`enterprises.1271.2.2.<mib>.0.<n>`), and a receiver that translates them to names would send every Ciena trap to the fallback item. The Ciena MIB set itself is available to Ciena customers from the Ciena Customer Portal (my.ciena.com).

Platform notes:

- SAOS 10 devices identify themselves with `sysObjectID` under `1.3.6.1.4.1.1271.1.2` (CIENA-PRODUCTS-MIB) (for example `.22` for a 5164 and `.39` for a 3984) and a `sysDescr` of the form `Ciena Corporation, CN5164 SAOS Operating System, Version saos-10-12-00-0228`. Devices running SAOS 6 or SAOS 8 use the WWP-LEOS MIBs instead and are covered by the official "Ciena 3906 by SNMP" template.
- Which traps a platform sends differs: module state change only on modular chassis (3926, 5171, 8110, 8114, 8180); dying gasp on 392x/3931, 394x, 513x, 5144, 516x, 5170/5171 and 8114/8180 but not on 398x, 5169, 518x or the other 81xx; dying gasp is never sent over SNMPv3.
- CIENA-CES-MODULE-MIB operational state and last reboot reason may read 0 on fixed-configuration platforms; the module triggers ignore 0.
- SAOS recommends at most two parallel SNMP walk / GetBulk requests per device. The template polls everything through a small number of `walk[]` master items; keep `{$SNMP.TIMEOUT}` generous and avoid stacking several SNMP templates on one host.

## Requirements

Zabbix version: 7.4 and higher.

## Tested versions

This template has been tested on:

- Ciena 3984, SAOS 10.12.00 (hardware, sysObjectID 1.3.6.1.4.1.1271.1.2.39): SNMP v2c polling and traps
- Ciena 5164, SAOS 10.12.00 (hardware, sysObjectID 1.3.6.1.4.1.1271.1.2.22): SNMP v2c polling and traps
- Ciena 5164, SAOS 10.12.00 (virtual node): SNMP v2c and v3 polling, traps
- Ciena 5164, SAOS 10.09.02 (replayed SNMP walk): v2c polling

Other SAOS 10 platforms share the same MIB object tables and notification definitions (SAOS 10.12 Fault and Performance Management guide), but have not been verified with this template; feedback is welcome.

## Setup

### 1. SNMP agent on the SAOS 10 device

The SNMP agent is enabled by default on SAOS 10 but ships with no community, no USM user, no VACM view and no trap target. The examples below create a read-only view of the whole tree, a v2c community, a v3 authPriv user and a trap target. Replace `<community>`, `<user>`, `<auth-password>`, `<priv-password>` and the Zabbix address `192.0.2.10` with your own values. SAOS 10 applies each line as it is entered (there is no `commit` unless the candidate datastore has been activated); leave configuration mode with `exit`, and save a backup copy with `config backup filename <name>.xml` if your operating procedure requires one.

Read-only view used by both versions:

```
config
snmp vacm view zabbixRO include iso
```

SNMPv2c (read-only community):

```
snmp community zabbixV2c text-name <community> security-name zabbixSecV2c
snmp vacm group zabbixGroupV2c member zabbixSecV2c security-model v2c
snmp vacm group zabbixGroupV2c access "" v2c no-auth-no-priv context-match exact read-view zabbixRO
snmp vacm group zabbixGroupV2c access "" v2c no-auth-no-priv context-match exact notify-view zabbixRO
```

SNMPv3 (authPriv, SHA/AES; SHA-224/256/384/512 and AES-192/256 are also supported):

```
snmp usm local user <user> auth sha password <auth-password>
snmp usm local user <user> priv aes password <priv-password>
snmp vacm group zabbixGroupV3 member <user> security-model usm
snmp vacm group zabbixGroupV3 access "" usm auth-priv context-match exact read-view zabbixRO
```

Trap target (SNMPv2c traps to the Zabbix trap receiver on UDP 162; the notify tag links the target to the notification table):

```
snmp target-params zabbixTrapParams v2c security-name zabbixSecV2c
snmp target zabbixTrapTarget target-params zabbixTrapParams udp ip 192.0.2.10 port 162
snmp target zabbixTrapTarget tag zabbixTrapTag
snmp notify zabbixNotify type trap tag zabbixTrapTag
exit
```

Use `show snmp state` to confirm the agent is running and `snmpwalk -v2c -c <community> <device> 1.3.6.1.2.1.1` from the Zabbix server to confirm reachability. The device needs a valid software license for the SNMP engine to start.

### 2. Zabbix host

1. Import `template_ciena_saos10_snmp.yaml` (Data collection → Templates → Import).
2. Create the host with an **SNMP interface** on UDP 161. For v2c set the community (`{$SNMP_COMMUNITY}` host macro, type *Secret text*); for v3 set the security name, authPriv, SHA and AES with the passphrases in secret host macros.
3. Link the template **Ciena SAOS 10 by SNMP**.
4. Check *Latest data* after a few minutes: system items first, then the discovered interfaces, filesystems, sensors, modules and transceivers (transceiver thresholds are refreshed hourly, diagnostics every 5 minutes).

### 3. SNMP traps in Zabbix

1. Run `snmptrapd` with a Zabbix trap handler and point the server at its log file (`StartSNMPTrapper=1`, `SNMPTrapperFile=/var/lib/zabbix/snmptraps/snmptraps.log`). Any receiver that writes the Zabbix trap file format (a header line with `ZBXTRAP <source address>` followed by the varbinds) works: the `zabbix/zabbix-snmptraps` container (ISO 8601 header timestamps, for example `2026-10-31T10:44:44+0000`) or `zabbix_trap_receiver.pl` with its default `hh:mm:ss yyyy/MM/dd` header timestamps. The trap items set no log time format, so they work with either header format, and the time shown for a trap is the time the Zabbix server read it from the file (normally within a second of reception). See [SNMP traps](https://www.zabbix.com/documentation/7.4/manual/config/items/itemtypes/snmptrap) in the Zabbix manual.
2. Zabbix matches a trap to a host by the source address of the trap and the host's SNMP interface address; the device must send traps from the address configured on the Zabbix host interface.
3. Do not install the Ciena MIBs on the trap receiver (or run `snmptrapd` with numeric output, `-On`). The `snmptrap[...]` expressions match the numeric notification OIDs as `snmptrapd` prints them without Ciena MIBs (`SNMPv2-SMI::enterprises.1271.2.2.<mib>.0.<n>`); with the MIBs loaded the traps would print as `CIENA-CES-...-MIB::...`, every Ciena trap would land in `SNMP traps (fallback)` and the chassis/PSU/fan/AAA state items would stop updating. Standard traps are matched by both name and number, so the standard MIBs shipped with `snmptrapd` are fine. Use the fallback item's history to see the exact text when adjusting an expression.
4. An administrative disable of a port that has an optic is reported by CIENA-CES-PORT-XCVR-MIB bias-low and Tx-power-low notifications (1271.2.2.9.0.13, .16) when the laser is switched off, followed by the matching "normal" notifications (.14, .17) on enable; the template classifies the former as "Transceiver threshold crossing reported" (Warning). These notifications carry no admin-state, so the template cannot tell a shut port from a failing laser: **shutting down a port that has an optic raises "Transceiver threshold crossing reported"**, which closes after `{$CIENA.TRAP.WINDOW}` or can be closed manually (`{$IFCONTROL}` only applies to the polled "Link down" trigger). IF-MIB linkDown/linkUp are sent only for a real operational change; a port that had no link does not emit them.
5. The event-type trap triggers (device restart, configuration change, SNMP authentication failure, routing protocol session down, module state change, dying gasp, CFM fault, transceiver threshold crossing, platform hardware) close automatically after `{$CIENA.TRAP.WINDOW}` (10 minutes by default) without a new matching trap, and can be closed manually. Chassis health and the TACACS+ / LDAP "all servers down" problems follow the state of the last notification and recover on the "good" or server status notification. "Power supply fault reported", "Fan speed out of range reported", "Transceiver removed, faulty or uncertified" and "L3VPN VRF down or EVPN Ethernet segment failure reported" do not recover automatically: each matching notification opens its own problem, which is closed manually once the unit is back (see [Known limitations](#known-limitations)).

### 4. Tuning

- `{$NET.IF.IFTYPE.MATCHES}` (`^(6|161)$`) selects physical ports and LAGs. Widen it to `^(6|53|161)$` to also discover SAOS logical ports, or filter by `{$NET.IF.IFNAME.MATCHES}` / `{$NET.IF.IFALIAS.MATCHES}` to monitor only service-facing ports.
- Use context macros per object where needed, for example `{$IFCONTROL:"23"}` = `0` to silence link-down alerts on port 23, `{$CIENA.TEMP.CRIT:"switch-temperature"}` = `85`, or `{$VFS.FS.PUSED.MAX.WARN:"/mnt/log"}` = `90`.
- SAOS 10 keeps `ifAdminStatus` = up(1) on the physical port row (ifType 6) when a port is administratively disabled and reports the admin-state on the logical port row (ifType 53) that has the same `ifName`. The interface discovery copies that admin-state to the physical port (`{#IFADMINSTATUS}`, with the logical row index in `{#CIENA.IF.ADMIN.INDEX}`), and the "Operational status" item reads that admin-state together with the operational state from the same walk value and reports adminDown (100) while the port is disabled. "Link down" depends on that one item only, so it does not fire for a port that is shut down (not even as a zero-length problem), an open "Link down" problem closes when the port is disabled, and re-enabling a port that has no link yet does not raise it. With the default `{$NET.IF.IFADMINSTATUS.NOT_MATCHES}` (`^2$`) a disabled port is also left out of discovery (an already discovered port becomes a lost resource and is rediscovered when it is enabled again); set the macro to `CHANGE_IF_NEEDED` to keep disabled ports. A physical port without a logical port row of the same name uses its own row; if "Link down" still fires for an intentionally disabled port, set `{$IFCONTROL:"<port>"}` = `0` or exclude it with `{$NET.IF.IFNAME.NOT_MATCHES}`.
- Transceivers with no light (Rx power at or below `{$CIENA.XCVR.RX.NOLIGHT}`, default -39 dBm; 0 uW is reported as -40 dBm) are excluded from the "Rx power is below the alarm threshold" trigger, so unpatched ports do not raise a problem per port out of the box. Set `{$CIENA.XCVR.RX.LOS.ALERT}` to `1` (template-wide or with the port name as context) to get a "No optical input" problem for ports that must always be lit.
- CPU utilization is computed from the UCD-SNMP-MIB `ssCpuRaw*` tick counters over a 5-minute window (the counters are polled every 3 minutes because SAOS 10 advances them only about once a minute); the percentage objects (`ssCpuIdle` and friends) are not used because some devices or records report `ssCpuIdle` = 0.
- SAOS 10 exposes no fan or PSU status object over SNMP GET: a stopped fan reads 0 rpm, and on platforms with PSU voltage telemetry (for example the 5164, 12 V) a PSU without input or with a fault reads 0 V. Platforms without that telemetry (for example the 3984) report 0 V for every PSU, healthy or not. The "Output voltage is too low" trigger therefore only fires for a PSU that has reported a non-zero voltage within the 24 hours before the drop, so a 3984 never alerts on it and a PSU that was already dead when monitoring started is not reported by polling; the PSU faulted traps cover both cases. Once raised, the problem stays open, however long the PSU stays down, until the voltage has been at or above `{$CIENA.PSU.VOLTAGE.MIN}` for 5 minutes. `{$CIENA.FAN.SPEED.MIN}` and `{$CIENA.PSU.VOLTAGE.MIN}` set the thresholds.
- CPU utilization is unsupported for its first evaluation after the host is created or the template is linked (the 5-minute window of counter rates is still empty, so the calculated item divides by zero); it recovers at the next 3-minute evaluation without any action.

### Known limitations

- LLDP-MIB, ENTITY-SENSOR-MIB, BGP4-MIB/OSPF-MIB/ISIS-MIB tables and HOST-RESOURCES hrProcessorTable are not implemented by the SAOS 10 SNMP agent; routing protocol state is available as traps only (and over gNMI/NETCONF outside the scope of this template).
- CIENA-CES-CHASSIS-MIB PSU/fan/temperature tables are not readable over SNMP GET on SAOS 10; LM-SENSORS-MIB and traps are used instead. PSU input voltage/current (LM-SENSORS misc table) is not collected.
- On SAOS 10.12.00 hardware the laser bias current (`cienaCesPortXcvrBias`) and its alarm thresholds read 0 for every optic although the CLI shows the real values; the item then shows 0 mA and the bias trigger stays inactive (it requires a non-zero high threshold).
- PSU output voltage is platform dependent: the 5164 reports it (12 V), the 3984 reports 0 mV for every PSU. The PSU voltage trigger therefore only fires for PSUs that reported a non-zero voltage in the 24 hours before the drop (it then stays open until the voltage is restored); use the power supply traps for platforms without voltage telemetry.
- Transceiver rows with a supply voltage of 0 (empty cage, DAC without diagnostics) are not discovered; transceivers that report no alarm thresholds get no threshold triggers. Rx/Tx power is converted from microwatts to dBm, with 0 uW shown as -40 dBm.
- The RMON CRC/alignment counter is mapped to the interface through `etherStatsDataSource` and is created for physical ports only; on a device without RMON rows the value is discarded and the item stays empty.
- **Power supply, fan, transceiver inventory and VRF / EVPN segment traps are not tracked per unit.** The PSU and fan notifications could not be captured from hardware during validation, and the transceiver and VRF notifications identify the port or VRF only in the varbinds, which the template does not parse into per-unit state. So that a clear from one unit never closes another unit's fault, "Power supply fault reported", "Fan speed out of range reported", "Transceiver removed, faulty or uncertified" and "L3VPN VRF down or EVPN Ethernet segment failure reported" do not recover automatically: every faulted notification opens its own problem, to be closed manually after checking the trap text and the device. The PSU and fan state items show the last notification of any unit. The polled per-PSU "Output voltage is too low" and per-fan "Speed is too low" triggers recover on their own.
- "Routing protocol session down reported" fires only for down events that can be read from the trap: BGP backward transition, CIENA-CES-LDP-MIB session down, OSPF neighbour state down(1), IS-IS adjacency down/failed (matched by the `isisAdjState` name, so only when the receiver has ISIS-MIB loaded) and OSPF interface authentication failure. The OSPF and IS-IS state varbinds are read in both the `zabbix/zabbix-snmptraps` and the `zabbix_trap_receiver.pl` line formats. bgpEstablished, LDP session up and other OSPF/IS-IS state changes do not raise it; BFD session state changes and BGP max-prefix notifications are recorded in "Routing protocol traps" but raise no problem, because their state is only in Ciena varbinds. The problem is device-wide: the next routing notification that is not a down event closes it, whichever peer it concerns.
- Shutting down a port that has an optic raises "Transceiver threshold crossing reported" (laser off is reported as bias-low / Tx-power-low and the trap carries no admin-state). The polled interface and transceiver triggers are not affected.
